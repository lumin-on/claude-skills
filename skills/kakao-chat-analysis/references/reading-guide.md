# 읽기 가이드: 구간 노트, 서브에이전트 프롬프트, analysis.json 스키마

## 1. 구간 노트 양식 (직접 읽을 때도 이 순서로 메모한다)

날짜마다 그날 나온 주제를 시간순으로 적는다. 주제 하나에 다음 항목:

- **제목** — 짧게. 변화가 있으면 `A → B`로.
- **범위** — `#id~#id`, 시간대
- **시작 / 참여** — 누가 꺼냈고 누가 받았나
- **내용** — 3~6문장. 주장·숫자·결정·공유된 링크/파일·쓰인 AI 도구
- **상태** — done / assigned(누가 무엇을) / open(다음 날로 이어짐) / drop(응답 없이 사라짐, 조언 기각) / info
- **톤** — 갈등·격려·불안·자랑 등 두드러질 때만

그리고 구간 끝에:

- **날짜를 넘어 이어지는 스레드** — 이름, 등장한 날들, 어떻게 변했나(X로 시작 → Y가 됨)
- **인물·조직·제품 용어집** — 처음 보는 고유명사마다 문맥에서 알 수 있는 것, 불확실하면 (추정)
- **화자별 관찰** — 무엇을 가져오는가, 누구에게 어떻게 반응하는가, 근거 발화
- **결정·약속·요청 표** — #id, 누가→누구에게, 내용, 구간 내 이행 여부(이행/미이행/불명)
- **미응답으로 끝난 발화 목록** — 질문·요청·경고 뒤 답이 없던 것

## 2. 서브에이전트용 읽기 프롬프트

큰 파일을 나눠 맡길 때 아래를 그대로 주고, `{...}` 만 채운다. 에이전트가 파일을 부분만 읽고 요약하려는 경향이 있으니 "전부 읽는다"를 명시한다.

```

참여자: {화자 목록과 알려진 관계}. 파일 형식: `#id [HH:MM] 화자: 본문` (여러 줄 메시지는 다음 #id 전까지 이어짐).
"사진", "이모티콘", "파일: ..." 은 미디어 표시다. 긴 붙여넣기(광고 카피, 공지문, AI 산출물)는 그 사람의 말이 아니라 가져온 자료다 — 누가 왜 가져왔는지만 적는다.

다음 파일을 처음부터 끝까지 전부 읽는다(부분 읽기·건너뛰기 금지):
{chunks 경로 목록}

결과를 {notes/partN.md} 에 저장하고 본문도 답으로 돌려준다. 다음 제목을 그대로 쓴다.

## 1. 날짜별 주제 타임라인
날짜마다 모든 주제를 시간순으로. 주제별로 제목 / 범위(#id~#id, 시간) / 시작·참여 / 내용(3~6문장, 숫자·결정·링크·파일·AI 도구 포함) / 상태(해결됨·담당자 지정(누가 무엇을)·진행중(다음날로 이어짐)·흐지부지(응답 없이 사라짐)·단순 정보공유) / 톤.
## 2. 날짜를 넘어 이어지는 스레드
이 구간에서 여러 날 등장한 주제: 이름, 날들, 어떻게 변했나. 구간 마지막 날에 열려 있으면 "다음 구간으로 이어짐"이라고 표시.
## 3. 인물·조직·제품 용어집
등장하는 모든 고유명사와 별칭. 문맥에서 알 수 있는 정체와 화자들과의 관계. 불확실하면 (추정).
## 4. 화자별 역할·성향 관찰
각 화자가 무엇을 가져오는지(정보·실행·검토·요청·격려), 누구에게 어떻게 반응하는지, 근거 발화 #id.
## 5. 결정·약속·요청 표
#id | 누가→누구 | 내용 | 구간 내 이행(이행됨/미이행/불명)
## 6. 미응답으로 끝난 발화와 눈에 띄는 패턴
질문·요청·경고 뒤 답이 없던 것, 반복되는 갈등, 정보가 어디서 들어와 누가 받는지.

비밀번호·계좌번호·전화번호는 옮기지 말고 "노출됐다"고만 적는다. 근거는 #id로 단다. 어떤 날도 건너뛰지 않는다.
```

## 3. 병합 규칙 (구간 노트 → analysis.json)

1. 같은 실체(사람·사업·문서·결정)가 다른 날 나오면 하나의 스레드. 구간 경계에서 "다음 구간으로 이어짐"으로 표시된 것을 먼저 이어 붙인다.
2. 제목은 `실체: 변화1 → 변화2 → 변화3`. 결과가 없으면 마지막 상태를 적는다.
3. `flow`는 날짜 태그를 앞에 붙여 `8/21 ... → 8/24 ... → 9/5 ...`로 쓴다. 누가 말했는지가 드러나야 한다.
4. `end`는 결말과 그 근거 발화. 열린 스레드면 "무엇이 확인돼야 닫히는지"를 `next`에 적는다.
5. 상태는 마지막 언급 기준. 담당자가 정해졐으나 이행 확인이 없으면 `done`이 아니라 `assigned`.
6. 하루짜리 잡담·단발 링크는 스레드로 만들지 않고 `daily` 다이제스트에만 남긴다.
7. 그룹은 4~7개. "이 방에서 굴리는 일"이 한눈에 보이도록 사업·영역 단위로. 가족·개인 이야기가 있으면 별도 그룹으로 둔다(사업 논의 사이의 완충 역할이 보인다).

## 5. 핵심 요약·다이제스트·프로필 작성 규칙

**핵심 요약(summary) 5~8개** — 이 순서로 채우면 보고서를 여기만 읽어도 된다.
1. 이 방이 무엇을 굴리는 방인지(사업·활동의 갈래 수, 대화의 무게중심)
2. 가장 긴 스레드 하나의 흐름을 한 줄로(시작 → 전환 → 현재)
3. **실제로 닫힌 일** — 누가 닫았는지
4. **답 없이 사라진 일** — 누가 물었고 누가 안 답했는지
5. 역할 구조(누가 꺼내고, 누가 만들고, 누가 걸러내는지)
6. 반복되는 패턴(번복, 위임의 비대칭, 갈등이 덮이는 방식 등)
7. 보안·민감정보가 노출됐다면 그 사실(내용은 옮기지 않음)

**날짜별 다이제스트(daily)** — 하루 한 줄, 시간순, 사람 이름과 숫자를 넣고 `→`로 잇는다. 결정·요청·무응답을 `<b>`로 강조해도 좋다. 조용한 날은 "○○ 링크만 공유, 응답 없음"처럼 적어 리듬이 보이게 한다.

**화자 프로필(speakers[].profile)** — `<p>` 두 개. 첫 단락: 무엇을 가져오는가(정보·실행·검토·요청·격려)와 근거 발화 인용. 둘째 단락: 다른 화자에게 어떻게 반응하는가(요청에 즉답하는지, 조언을 기각하는지, 물러나는지). `role`은 "첫째 · 사업 총괄, 정보 유입, 최종 결정"처럼 관계·역할 키워드 3개 안팎.

**스레드 flow** — `8/21 ... → 8/24 ... → 9/5 ...` 날짜 태그 + 누가 무엇을 했는지. 5~10문장. 짧은 인용은 그 사람 말투 그대로. `end`는 결말과 근거 발화, `next`는 열린 스레드가 닫히려면 무엇이 확인돼야 하는지.

## 6. 완료 기준 (렌더 전 체크리스트)

`build_report.py`가 `check_analysis.py`로 자동 검사한다. 오류는 렌더를 막고, 경고는 출력만 한다.

- [ ] 모든 날짜에 다이제스트가 있다 (오류)
- [ ] 화자 프로필의 이름이 stats.json의 이름과 정확히 같다 (오류) — 소규모 방은 전원, 오픈채팅은 상위 5~8명+운영자
- [ ] 모든 스레드에 title·group·status·flow가 있고 status는 5개 코드 중 하나 (오류)
- [ ] 스레드의 group이 groups에 존재한다 (오류)
- [ ] 요약 5~8개, 각 40자 이상 (경고)
- [ ] flow는 120자 이상, `→`와 날짜 태그 포함 (경고)
- [ ] open·assigned·drop 스레드에 next, done 스레드에 end (경고)
- [ ] 열려 있거나 사라진 스레드가 최소 하나는 있다 — 없다면 무응답 질문을 놓친 것 (경고)
- [ ] notes에 파싱 각주와 민감정보 처리 문구 (경고)

사람이 볼 것: 스레드 제목만 훑어도 이 방의 22일이 이해되는가, "열려 있거나 사라진 것" 표에서 누구를 찔러야 하는지 바로 보이는가, 인용이 원문 말투를 지켰는가.
