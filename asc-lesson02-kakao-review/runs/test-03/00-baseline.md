# 왜 이 세 가지를 붙였나 — 이전 실행에서 나온 실측

오픈소스를 고른 근거는 추측이 아니라 **실제 대화 11,341줄로 돌려 보고 나온 실패**다.
그 실행(runs/test-02)은 개인정보가 포함된 실제 카카오톡 내보내기를 썼으므로 **결과물을 저장소·제출물에 넣지 않는다.** 아래는 숫자만 옮긴 것이다.

## 이전 실행에서 터진 문제

| 문제 | 실측 | 원인 |
|---|---|---|
| 원문 마지막 줄이 어느 청크에도 안 들어감 | 11,341줄 중 1줄 누락 | 파일 끝에 개행이 없어 `wc -l`이 11,340을 반환, 그 값으로 청크 계획을 세움 |
| 인용 줄 번호 어긋남 | 인용 1,214건 중 **16건**(1.3%) | 분석 Subagent가 긴 파일을 Read의 offset/limit으로 나눠 읽으며 오프셋이 밀림. 인용 문구 자체는 원문에 있고 줄 번호만 1~70줄 어긋남 |
| 올바른 줄 찾기 | 16건을 사람이 ±50줄 훑고 grep | 자동 탐색 수단이 없었음 |
| 상태값 오타 | `해결·정` 2건 (허용값은 `해결·결정`) | 검증 규칙이 `scripts/core.mjs`에 하드코딩돼 있어 위반 위치를 짚기 어려움 |
| 청크 분할 | 7청크를 글자 수 눈대중 | 토큰을 세지 않아 문맥 초과 위험을 감으로 관리 |

## 새 도구로 같은 데이터를 다시 검사한 결과

세 스크립트를 만든 뒤, 이전 실행 결과에 그대로 돌려 **사람이 손으로 찾았던 것을 재현하는지** 먼저 확인했다.

```
RapidFuzz  : 인용 1214건 검사 / 불일치 16건 / 자동 교정 가능 15건
             → 손으로 찾은 16건과 정확히 일치. 15건은 올바른 줄 ID까지 제시.
             → 1건("그럴듯")은 짧은 문구라 여러 줄에 나타나 자동 교정 불가로 표시(정직한 한계)
ajv        : 분석 결과 7개 파일 중 2개 FAIL
             /topics/5/status  enum: must be equal to one of the allowed values   (c1-T06)
             /topics/1/status  enum: must be equal to one of the allowed values   (c7-T02)
             → 손으로 찾은 오타 2건을 JSON Pointer 위치까지 짚어냄
tiktoken   : 줄 11,341 / 토큰 276,546 / 청크 17 (예산 25,000) / 커버리지 완전
             → 마지막 줄 누락 해소. 이전에 놓쳤던 L11341이 c17에 포함됨
```

> 위 실행 로그의 원본(인용 문구 포함)은 실제 대화 내용이라 제출물에서 제외했다.
> 숫자와 JSON Pointer 위치만 이 문서에 옮겼다.
